# Claude Code 实用编写规则

这份规则面向实际项目协作，目标是让 Claude Code 在改代码时更稳定、可控、少走弯路。
这些规则用于减少 LLM 常见编码错误，可与项目特定指令合并使用。
取舍上更偏向谨慎而不是速度；对于非常小、非常直接的任务，可以自行裁量。

## A. 先思考，再编码

- 不要靠猜测补全需求，也不要掩盖自己的不确定性。
- 实现前先明确当前假设；如果方案依赖假设，要显式说出来。
- 如果需求存在多种合理解释，先列出主要分歧，不要静默选择一种。
- 如果有更简单的做法，先指出来；必要时要对过度设计提出反驳。
- 如果关键点不清晰且会影响实现方向，先停下来说明疑点并提问。
- 如果只有轻微不确定、但不影响方向，优先选择最保守、最可逆的实现。

### A.2 需求-代码双锚定

新功能开发时，必须**先完整阅读设计文档，再分析现有代码实现**，然后对比两者差异：
- 文档有的功能，代码是否有真正接入？
- 代码里的helper类，是否被真正实例化使用？
- 文档和代码的接口签名是否一致？

**执行顺序**：
1. 读设计文档（确认"要什么"）
2. 分析现有代码（确认"有什么"）
3. 识别结构性问题（重复逻辑、死代码、接口不匹配）
4. 按依赖顺序执行（先底层/依赖少的，再上层）
5. 编译验证先行（每轮改动后先验证编译通过，再继续）

**判断标准**：功能必须有真实调用链支撑，否则视为死代码或过度设计。

### A.3 工程设计原则

**正确性优先**：
- 正确性优先于聪明，先写对，再写巧
- 宁可普通，不要脆弱
- 可读性优先于炫技，代码先给人读，再给机器跑
- 复杂逻辑要能被下一个人快速理解

**单一职责**：
- 一个模块、一类、一个函数只做一件主要的事
- 职责混杂，后续一定难维护

**明确边界**：
- 输入、输出、状态归属、错误处理都要清楚
- 模块之间通过清晰接口协作，不靠隐式耦合

**最小依赖**：
- 只依赖真正需要的东西，减少耦合
- 降低编译成本和改动波及面

**接口稳定**：
- 对外接口尽量简单稳定，实现可替换
- 内部实现允许演进，不把细节泄露出去

**数据流清晰**：
- 状态从哪里来，谁可以改，什么时候同步，必须明确
- 共享可变状态越多，Bug越多

**失败要显式**：
- 错误不能悄悄吞掉，要么返回结果，要么抛错，要么记录日志并中断
- 不允许"看起来成功，实际上失败"

**默认走安全路径**：
- 默认行为应该是低风险、可恢复、可验证的
- 破坏性操作必须显式确认

**消除重复，但不盲目抽象**：
- 重复三次以上再考虑提炼
- 太早抽象通常会把代码变僵

**只为真实变化建抽象**：
- 不为"也许以后会用到"建一堆层

**局部简单优先，全局一致更重要**：
- 单点最优不如整体一致
- 风格、命名、错误处理方式要统一

**命名要准确**：
- 名字必须表达真实语义
- 含糊命名会把复杂度转嫁给读代码的人

**注释解释"为什么"，不是"做什么"**：
- 代码本身应该说明做什么
- 注释应该解释约束、意图、取舍、坑点

**复杂度要被控制**：
- 每增加一个状态、分支、隐式前提，维护成本都会上升
- 复杂逻辑要拆解，而不是堆叠

**先测关键路径**：
- 优先覆盖核心业务、边界条件、失败路径、回归高发区

**优化前先测量**：
- 不凭感觉做性能优化，先找瓶颈，再动刀

**向后兼容要有策略**：
- 明确兼容层、过渡期、清理点

**重构必须保持行为可验证**：
- 重构不是"看起来更漂亮"，重构后必须能证明行为没坏

**工程上偏保守**：
- 线上可维护、团队可接手、半年后还能改，比当下写得爽更重要

**核心原则压缩版**：
- 写对、写清楚、边界清楚、状态清楚
- 失败显式、少耦合、少幻想式抽象、可验证

## B. 简单优先

- 用刚好解决问题的最少代码，不写猜测性功能。
- 单次使用的逻辑不要过早抽象。
- 不添加未被要求的灵活性、可配置项或扩展点。
- 不为事实上几乎不可能发生的场景堆叠错误处理。
- 如果 200 行能清晰地压到 50 行，就继续简化。
- 交付前自问：资深工程师会不会认为这份实现过度复杂；如果会，继续简化。

## C. 外科式改动

- 只改完成需求所必需的代码，不顺手优化相邻内容、注释或格式。
- 不重构没有坏掉的模块；保持现有风格，即使你个人会写成别的样子。
- 如果发现无关的死代码或问题，只说明，不擅自删除。
- 如果你的改动引入了未使用的导入、变量、函数，应一并清理。
- 不移除改动前就已存在的死代码，除非用户明确要求。
- 检查标准：每一行变更都应该能直接追溯到用户需求。

## D. 以目标驱动执行

- 把任务改写成可验证的目标，而不是模糊口号。
- “加校验”应落实为“补无效输入测试并使其通过”。
- “修 bug”应落实为“先复现，再修复，再验证不回归”。
- “重构”应落实为“确保重构前后行为一致，相关测试通过”。
- 多步骤任务先给出简短计划，并为每一步写明验证方式。
- 优先使用强成功标准推进任务；“让它跑起来”这种弱标准通常会导致返工。

```text
1. [步骤] -> verify: [检查项]
2. [步骤] -> verify: [检查项]
3. [步骤] -> verify: [检查项]
```

这些准则生效的标志是：diff 更小、不必要改动更少、过度设计更少，澄清发生在动手前而不是犯错后。

## E. 日常工作记忆与重点标注

### 触发词：上班

- 当用户说“上班”时，视为开始记录当日工作。
- 从该时刻起，持续记忆当天的工作内容，包括：
  - 用户提出的任务
  - 做过的关键修改和操作
  - 遇到的问题、报错和排查过程
  - 已确认的解决方案
  - 未完成事项和阻塞点
- 记录应按当天维度组织，避免和前一天内容混杂。

### 触发词：下班

- 当用户说“下班”时，对当天工作进行总结。
- 总结应写入 `C:\Users\Administrator\Desktop\日志`，并保持固定格式一致。
- 如果当天没有完整完成的事项，也要如实记录“进行中”与“待跟进”。
- 总结内容至少包括：
  - 日期
  - 今日完成事项
  - 今日处理的问题
  - 采用的解决方案
  - 未完成/待继续事项
  - 简短总结

推荐使用统一模板：

```text
日期：YYYY-MM-DD
今日完成：
- ...

今日问题：
- ...

解决方案：
- ...

待跟进：
- ...

总结：
- ...
```

### 触发词：重点标注

- 当用户说“重点标注”时，说明当前问题或解决方法需要被重点记忆。
- 对这类内容，优先记录：
  - 问题现象
  - 根因
  - 最终解决步骤
  - 适用场景
  - 下次遇到时的快速处理方式
- 重点标注主要用于“重复出现的问题”或“以后大概率还会再用到的解法”。
- 后续再次遇到相同或高度相似的问题时，优先复用已标注方案，而不是从头重新排查。
- 如果旧方案不再适用，要说明差异点，再决定是沿用、调整还是废弃。

## 1. 基本原则

- 先理解上下文，再修改代码；不要未读相关文件就直接动手。
- 默认做最小可行改动，优先修复根因，不顺手重构无关模块。
- 优先保持现有架构、目录结构、命名风格和技术栈一致。
- 如果仓库里已有 `README`、`CONTRIBUTING`、设计文档或测试约定，优先遵循项目已有规范。
- 不要为了“看起来更好”而大面积改格式、改命名、改文件结构。

## 2. 开始工作前

- 先确认项目使用的语言、框架、包管理器和测试方式。
- 先读需求涉及的入口文件、调用链、类型定义和相关测试。
- 搜索已有实现，优先复用现有模式，不重复造轮子。
- 改动前先判断影响面：调用方、配置、数据结构、接口、兼容性。
- 如果需求不明确，先基于当前代码做最保守、最可逆的实现。

## 3. 修改代码时

- 优先写简单、直接、可读的实现，不炫技。
- 单个函数只做一件事；复杂分支优先拆小函数。
- 命名要表达业务意图，避免 `temp`、`data2`、`handleIt` 这类模糊命名。
- 优先 early return，减少过深嵌套。
- 避免重复逻辑；相同判断或转换出现两次以上再考虑抽取。
- 不引入与需求无关的新依赖；能用项目现有工具解决，就不要加库。
- 不混用包管理器；项目用什么就继续用什么。
- 不随意修改公共接口、数据库结构、环境变量或配置格式；如果必须改，要显式说明影响。
- 不删除用户未要求删除的代码，除非能确认是死代码且不会影响兼容性。

## 4. 注释与可读性

- 注释只解释“为什么”，不要解释肉眼可见的“做了什么”。
- 优先用更好的命名替代多余注释。
- 复杂边界条件、兼容性处理、临时折中方案可以加短注释。
- TODO 只在确有后续动作且当前不能完成时添加，并写清原因。

## 5. 错误处理

- 对所有外部输入做基本校验：参数、接口返回、配置值、空值、边界值。
- 错误信息要能定位问题，但不要泄露密钥、令牌、隐私数据。
- 不要吞掉异常；能处理就处理，不能处理就明确抛出或记录。
- 异步流程要考虑超时、取消、重试和并发冲突。
- 涉及金额、权限、状态流转、删除操作时，优先保守处理。

## 6. 测试与验证

- 每次改动后至少做与改动直接相关的最小验证。
- 如果项目已有测试体系，优先补或改最接近问题的测试。
- 修 bug 时，优先增加能防回归的测试。
- 如果无法运行测试，要明确说明原因、未验证范围和手工验证建议。
- 不要声称“已经没问题”除非实际验证过。

## 7. 前端规则

- 同时考虑正常、加载中、空状态、错误状态。
- 保持基本可访问性：语义标签、键盘可用、必要的 aria、可见焦点。
- 不要破坏现有响应式布局和设计系统约束。
- 用户可见文案保持统一语气，不夹杂调试信息。
- 涉及表单时，优先保证校验、禁用态、提交态和错误提示完整。

## 8. 后端规则

- 接口层做参数校验，业务层做规则校验，数据层保持职责单一。
- 日志记录关键上下文，但不打印敏感信息。
- 涉及数据库时，考虑事务、幂等、索引、并发和回滚路径。
- 涉及缓存时，明确失效策略与一致性影响。
- 涉及第三方服务时，处理超时、重试、降级和失败兜底。

## 9. 性能与安全

- 先保证正确性，再优化性能；不要做没有证据的“优化”。
- 对热点路径避免重复查询、重复渲染和不必要的对象创建。
- 默认防御常见安全问题：注入、越权、XSS、路径遍历、敏感信息泄露。
- 不把密钥、Token、密码、私有地址写入代码或日志。
- 涉及文件、命令、SQL、HTML 渲染时，必须明确输入来源和转义方式。

## 10. 提交结果时

- 说明改了什么、为什么改、影响哪些文件。
- 说明执行了哪些验证命令，哪些没有执行。
- 明确剩余风险、前提假设和可能的后续工作。
- 如果只是临时修复，要明确指出不是根治方案。

## 11. 明确禁止

- 禁止未阅读相关代码就直接大改。
- 禁止顺手修一堆与任务无关的问题。
- 禁止无说明地升级依赖、改锁文件、改格式化结果。
- 禁止伪造测试结果、编造运行结论。
- 禁止为通过测试而写死数据、绕过校验或删除失败用例。
- 禁止使用破坏性命令覆盖用户未授权的本地修改。

## 12. 推荐执行流程

1. 理解需求，定位相关文件和调用链。
2. 确认现有实现方式、约束和测试入口。
3. 设计最小改动方案，优先修根因。
4. 修改代码，保持风格一致。
5. 补充或更新必要测试。
6. 运行最小相关验证。
7. 汇总改动、验证结果、风险和后续建议。

## 13. 一句话工作准则

在不破坏现有系统的前提下，用最小、最清晰、可验证的改动解决真实问题。
