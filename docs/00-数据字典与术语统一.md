## 1. 阶段定义（范围分期）

平台按三阶段交付，所有功能/表/接口须标注归属阶段。

| 阶段 | 主题 | 范围要点 |
| --- | --- | --- |
| **阶段一** | 核心闭环 MVP（可上线） | Project + Requirement + Task + Sprint/Kanban 为一等公民；个人工作闭环（任务→日志→AI 规则分析→人工确认→完成度）；测试缺陷；简化 RBAC；基础健康度报表；一级导航 6 项 |
| **阶段二** | AI 文档闭环 + 协作 | 文档上传→异步 AI Job→分析→人工确认→写入需求/任务；RAG 基础检索；真实报表/驾驶舱；通知；WebSocket 协同前端 |
| **阶段三** | 企业级扩展 | Program/Portfolio 战略层；流程模板引擎；多模型路由 + 文档密级 + 细粒度权限；标书分析；自动规划；完整报表矩阵；评论/@提及/订阅 |

> Program / Portfolio / Product 在**阶段一仅作为可选分组标签**（保留外键字段，不做独立管理菜单），阶段三才升级为完整管理域。

## 2. 状态枚举（统一值）

### 2.1 任务状态 `task.status`
取最完整规范的一套（原 05 文档版本）。**废弃** 03 的中文 8 态与 08 的 4 态简化版。

| 值 | 含义 | 阶段一可见 |
| --- | --- | --- |
| `todo` | 待处理 | 是 |
| `in_progress` | 进行中 | 是 |
| `blocked` | 阻塞 | 是 |
| `code_review` | 代码评审 | 是 |
| `testing` | 测试中 | 是 |
| `acceptance` | 待验收 | 是 |
| `done` | 已完成 | 是 |
| `cancelled` | 已取消 | 是 |

> Kanban 列 = 任务状态映射，**不另设独立字典**。看板列即上述状态的子集排列（阶段一建议列：`todo / in_progress / code_review / testing / done`）。`task.status` 为单一真源，废除前端 `data.js` 中 `running/waiting/in_review` 等别名。

### 2.2 缺陷状态 `defect.status`
统一 snake_case，**废弃**首字母大写写法（New/Confirmed/...）。

`new → confirmed → in_fix → resolved → verified → closed`（可旁路 `rejected`）

### 2.3 需求状态 `requirement.status`

`draft / reviewing / approved / in_dev / testing / accepted / closed / cancelled`

### 2.4 项目状态 `project.status`

`planning / active / on_hold / done / archived`

### 2.5 AI Job 状态机 `ai_job.status`
统一一套状态机，**废弃** 05 §2.10 仅含 `queued/running/completed/failed` 的简化版。

```
queued ──▶ running ──▶ awaiting_review ──▶ confirmed
                  │                    └─▶ rejected
                  └─▶ failed ──▶ retried ──▶ queued
```

| 值 | 含义 |
| --- | --- |
| `queued` | 已入队 |
| `running` | 执行中 |
| `awaiting_review` | 待人工确认（AI 结论已产出，未落库） |
| `confirmed` | 人工确认并写入业务数据 |
| `rejected` | 人工驳回，不落库 |
| `failed` | 执行失败 |
| `retried` | 失败后重试（回到 queued） |

> AI 结论**必须经 `awaiting_review` 人工确认后才落库**。前端须展示状态/进度/错误，并提供「确认写入 / 编辑后写入 / 忽略」三种操作。

## 3. 字段命名（统一）

取 05 文档命名为准，**废弃** 08 的 `sequence / linked_requirement_id`、以及 09 的驼峰混用。

| 标准字段（DB snake_case） | API（camelCase） | 说明 |

> **命名总则**：数据库列统一 snake_case，API 出入参统一 camelCase，由后端 mapper 转换（现有 `api/db.js` 的 `mapTask` 等即此职责）。

### 3.2 任务类型 `task.type`

`epic / story / task / bug / milestone / work_package`（同时承载 Scrum 三层与 WBS 工作包）。

## 4. AI 日志分析输出 Schema（统一）
合并 04 文档中三段不一致示例为单一结构。

```jsonc
{
  "analysisId": "uuid",
  "jobId": "uuid",
  "entities": [                    // NER 抽取的实体
    { "type": "requirement|task|defect", "refCode": "REQ-001", "confidence": 0.92 }
  ],
  "progressUpdates": [            // 进度信号
    { "targetType": "task", "targetId": "uuid", "deltaPercent": 20, "note": "完成接口联调" }
  ],
  "blockers": [                   // 阻塞项
    { "description": "等待第三方接口", "severity": "high" }
  ],
  "suggestedLinks": [            // 建议关联（待人工确认）
    { "fromType": "log", "toType": "requirement", "toId": "uuid", "confidence": 0.8 }
  ],
  "completionDelta": [          // 建议的需求完成度变化
    { "requirementId": "uuid", "suggestedScore": 65 }
  ],
  "nextPlan": ["明日继续 X 模块联调"]
}
```

> 置信度 `< 0.75` 的结论**仅作建议**，不自动应用，须人工确认。MVP（阶段一）实现路径：正则（`REQ-/TASK-/BUG-/百分比`）+ 业务词典 + LLM 结构化判断三层组合；专用 NER 模型微调属阶段三。

## 5. 需求完成度算法（统一）
**废弃**基础版，保留增强版一条：

```
完成度 = 关联任务完成率 × 0.40
       + 测试通过率     × 0.30
       + 日志进度       × 0.20
       + 人工确认       × 0.10
       − 风险扣减
```

**硬规则（不可被自动覆盖）**：
- 无测试关联 → 完成度 ≤ 80%
- 存在未关闭的阻塞缺陷 → 完成度 ≤ 70%
- AI 建议值与人工值差 > 15% → 报警，需人工裁决
- 待验收 + 测试通过率 < 90% → 禁止自动关闭需求

## 6. 通用约定

| 项 | 约定 |
| --- | --- |
| **后端端口** | **4010**（废弃 README 历史的 4000）。前端 Vite proxy `/api`、`/ws` 均指向 4010 |
| **前端端口** | 5173 |
| **分页响应** | `{ "items": [], "page": 1, "pageSize": 20, "total": 0 }` |
| **错误响应** | `{ "errorCode": "STRING", "message": "可读信息", "traceId": "uuid" }` |
| **状态变更** | 统一走 `PATCH /api/{resource}/{id}/status`，并写审计日志 |
| **ID 格式** | UUID |
| **时间格式** | ISO 8601（UTC），如 `2026-06-24T08:00:00Z` |
| **API 前缀** | `/api` |
| **鉴权** | JWT，有效期 8h；状态变更类接口校验权限 |

## 7. 权限模型（分阶段）

- **阶段一**：简化 RBAC = 角色（admin / pm / dev / test / viewer）× 资源粒度权限（如 `project:*`、`requirement:write`）。
- **阶段三**：在此之上叠加数据范围、文档密级、AI 能力权限等细粒度控制。

> 阶段一不实现 5 层叠加权限，避免过度设计。
