  - ✅ **已实现**：代码中存在且可用。

## 6. AI 能力差异

文档（04/08）描述完整 AI 管线（异步 Job 队列、RAG、多模型路由、NER）。实际：

| 能力 | 文档 | 代码实际 | 状态 |
| --- | --- | --- | --- |
| 文档分析 | 异步 Job + 结构化抽取 | 同步建 Job（status 直接 `awaiting_review`），**requirements/wbs/apis/risks 基本写死** | 🟡 |
| 真实 LLM 调用 | 多模型路由 | 所有聊天、摘要、文档分析和业务建议的 LLM 调用统一进入 **DeepSeek Harness** JSON-RPC runtime；平台保留 REST/RBAC/审计/Job/人工确认和业务写入。API 控制面解析活动 Provider，Harness 不再直连真实 Provider | ✅ |
| Provider Key 与出站 | 客户端可配置多 Provider | Provider Key 只由 API 控制面保存/读取；API 按需启动 `127.0.0.1` 随机端口代理并为每个 Harness runtime 下发一次性 token，子进程无真实 Key、JWT、数据库 URL 或种子凭据。`/models` 仍是受权限保护的控制面元数据发现例外，不属于推理路径 | ✅ |
| Harness 能力边界 | Agent / Tools 编排 | 首版仅启用受管文本/图片推理与本地 JSONL session/attachment 存储；workspace context、skills、bash、jobs、goals 均关闭。后续业务工具只能通过平台 RBAC、审计和审批边界接入 MCP | ✅ |
| 日志分析 | NER + LLM | **纯正则 + 词典规则引擎**（`REQ-\d+`、百分比、中英关键词） | ✅ 规则版（符合阶段一） |
| 完成度评分 | 加权算法 | 已实现加权 + 硬规则封顶 | ✅ |
| Job 状态机 | `queued→running→awaiting_review→confirmed/rejected/failed→retried` | 已具备本地 dispatcher、启动时 queued 恢复、running 中断失败、确认/驳回/重试，以及运行超时自动失败并写入 `ai.job_timeout` 审计；尚未外置 Redis/独立 Worker | 🟡 |
| RAG 检索 | 向量库检索 | 🟡 **hybrid**：关键词 + 本地确定性 hash 向量余弦相似度，写入 `embedding_*` 字段与 citation；不调用远程 embeddings；**无 pgvector** | 🟡 |
| AI 摘要面板 | — | `modelRoutes` 已改为基于当前 AI Provider 配置、启停状态、健康状态和已配置 Provider 数量实时生成；未配置/禁用/降级/不可用均有明确状态 | ✅ |

**结论**：阶段一"规则版 AI"目标已达成；阶段二的 AI Job 已具备本地异步执行、审核/驳回/重试、启动恢复和超时审计闭环。Harness 是唯一 AI 执行内核：调用超时或传输失败会关闭并重建受管 runtime，业务层可按既有规则安全降级；`/api/health` 仍只表示 API/数据库 readiness，不把 Provider 或按需启动的 Harness 作为公网存活探针。RAG as-built 为 **hybrid**（关键词 + 本地确定性 hash 向量 + citation + ACL），没有远程 Provider embeddings 旁路。外置队列/独立 Worker、**pgvector** 与完整多模型编排仍为目标态。
